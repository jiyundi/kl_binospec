# 裁切方案路径与失败计数

## 任务与进展

- 用户在 `data_prep` 目录用 PowerShell 对 slit 1..20 批量运行 `python main.py --slitID $i --crop_plan $cropPlan`，询问为何多个 slit 报错而最终只统计 1 个失败。
- 已定位两个原因，并给出修正后的批处理命令；本会话未修改项目代码，也未实际重跑整批数据。

## 诊断与依据

- `$cropPlan` 的值为 `slit_NNN_crops.json`，作为相对路径传入时从当前目录 `data_prep` 查找；真实文件在 `data_prep/spec_crop_plans/`。`main.py` 只有在不传 `--crop_plan` 时才自动使用该目录。
- `spec/crop_plan.py` 中 `read_plans()` 对不存在的文件返回空字典，因此 `main.py` 把所有指定发射线报告为 `missing lines`，错误信息本身未明确指出文件不存在。
- 已用只读 Python 检查报错涉及的 13 个文件：slit 3、5、7、8、10、13–20 的方案文件均存在于 `spec_crop_plans`，且其顶层谱线键与粘贴的 `missing lines` 列表一致。此次报错由路径造成，不能据此判断这些方案内容缺失。
- 粘贴的循环没有 `$failedSlits = @()`。已在 PowerShell 复现：从 `$null` 开始对上述 13 个整数执行 `+=` 得到单个整数 `165`，`.Count` 为 1；初始化为数组后 `.Count` 为 13。用户粘贴的最终统计为 1，旧输出文件曾显示单个值 `334`；该值不是失败 slit 列表，当前文件可能已被后续操作覆盖。
- `No secure redshift found` 和 `no line provided for cutting` 分支以退出码 0 跳过，不计入失败。

## 给用户的修正方案

在 `data_prep` 目录执行前先设 `$failedSlits = @()`；循环中调用 `python main.py --slitID $i`，不传 `--crop_plan`，使程序按 slitID 自动读取 `spec_crop_plans`；只有 `$LASTEXITCODE -ne 0` 才将编号加入数组，最后写入 `failed_slits.txt` 并报告 `.Count`。
